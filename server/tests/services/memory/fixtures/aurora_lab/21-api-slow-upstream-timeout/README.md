# 504 Gateway Timeout nginx: meaning and how to fix it

*504 Gateway Timeout means nginx gave up waiting on the upstream. Tell a slow upstream, an unreachable one and a too-low timeout apart, with real logs.*

Runbook for lab scenario `21-api-slow-upstream-timeout`. Canonical version, with its byline, kept current: https://www.aurorasre.ai/runbooks/fix-504-gateway-timeout-nginx-kubernetes. Written from the lab runs in this repository; updated 2026-10-29.

```
./lab.sh up
./lab.sh break 21-api-slow-upstream-timeout
```
Then investigate with any tool you like; `scenario.yaml` holds the ground truth and the grading criteria.

**A 504 Gateway Timeout means a proxy (nginx, an ingress controller, a load balancer) stopped waiting for the server behind it and answered the client itself; the upstream may be slow or unreachable, but it sent nothing in time.** In nginx the error log says which wait ran out: `upstream timed out (110: ...) while reading response header from upstream` means the upstream accepted the connection and did not answer within `proxy_read_timeout` (60s by default), and `while connecting to upstream` means it could not be reached within `proxy_connect_timeout`. Confirm which by timing one request straight to the upstream, bypassing the proxy. The usual fix is in the upstream (most often a dependency call with no timeout); raising the proxy timeout only makes users wait longer for the same slow answer.

## At a glance

| Signal | Likely cause | Confirm with | Fix |
|---|---|---|---|
| `while reading response header from upstream`, request time equals `proxy_read_timeout`, pods Ready, Service has endpoints | The upstream is slow, usually waiting on its own dependency | Time a request to the upstream directly; see what its threads wait on (`netstat -tn` in the pod) | Fix or time-box the slow call, or revert the change that added it |
| A share of requests 504 at exactly the timeout, the same endpoint's successes take just under it, nothing changed | The timeout is below the endpoint's normal latency | The upstream's own durations for that path | Raise the timeout for that location only, or make the work asynchronous |
| `while connecting to upstream`, request time equals `proxy_connect_timeout`, `$upstream_connect_time` is `-` | The upstream address drops packets: dead node, firewall, wrong IP, or a ClusterIP port the Service does not publish | Connect from the proxy's pod or host to the upstream address | Fix the routing or the address |
| 504 after two or three times the timeout, several addresses in `$upstream_addr` | nginx retried the timeout on other upstream servers (`proxy_next_upstream`) | The comma-separated upstream fields in the access log | Stop retrying timeouts, or cap the total with `proxy_next_upstream_timeout` |
| Client reports a timeout, nginx logs `499`, no 504 anywhere | The client gave up before nginx did | The client's timeout against `proxy_read_timeout` | Same as row 1: the upstream is slow |
| 502, not 504: `Connection refused` or `upstream prematurely closed connection` | The upstream answered with an error or nothing at all | The nginx error log | See [502 Bad Gateway in nginx and Kubernetes](https://www.aurorasre.ai/runbooks/fix-502-bad-gateway-nginx-kubernetes) |

## What does 504 Gateway Timeout mean?

[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-504-gateway-timeout) defines it in one sentence: the server, "while acting as a gateway or proxy, did not receive a timely response from an upstream server it needed to access in order to complete the request." Two things follow. The 504 is generated by the proxy, never by your application, so the application's own logs will not contain it. And "timely" is whatever the proxy was configured to wait, so the same slow upstream can produce a 504 at one hop and a client-side timeout at another.

The body tells you which hop gave up. Stock nginx (our run, nginx:1.27-alpine):

```
<html>
<head><title>504 Gateway Time-out</title></head>
<body>
<center><h1>504 Gateway Time-out</h1></center>
<hr><center>nginx/1.27.5</center>
</body>
</html>
```

If the footer names a different server (a cloud load balancer, a CDN), the timeout that fired is theirs, and the nginx below it may never have seen the request finish either way.

## 504 vs 502: how do the nginx logs differ?

We put one nginx in front of a small test upstream and produced each failure on purpose (Docker, nginx:1.27-alpine, `proxy_connect_timeout 2s`, `proxy_read_timeout 3s`, a log format that adds `$request_time`, `$upstream_connect_time` and `$upstream_header_time`). What the client got and what nginx wrote:

| Upstream behaviour | Client got | Time | nginx error log | `uct` / `uht` |
|---|---|---|---|---|
| Answers in 1s | 200 | 1.04s | nothing | 0.001 / 1.017 |
| Accepts, answers after 5s | 504 | 3.02s | `upstream timed out (110: Operation timed out) while reading response header from upstream` | 0.001 / - |
| Address drops packets (192.0.2.10) | 504 | 2.00s | `upstream timed out (110: Operation timed out) while connecting to upstream` | - / - |
| Port closed | 502 | 0.001s | `connect() failed (111: Connection refused) while connecting to upstream` | - / - |
| Accepts, closes without answering | 502 | 0.002s | `upstream prematurely closed connection while reading response header from upstream` | 0.000 / - |
| Sends a header, then one byte every 2s for 10s | 200 | 10.01s | nothing | 0.000 / 0.001 |
| Client gives up after 1s (upstream needs 5s) | nothing (curl `000`) | 1.01s | nothing; access log `499` | 0.001 / - |

The access log lines for the failing and slow cases, as written (trimmed: the 1 second 200 and the interleaved error log lines are left out):

```
192.168.156.1 [29/Oct/2026:15:56:53 +0000] "GET /app/sleep/5 HTTP/1.1" 504 rt=3.004 urt=3.004 uct=0.001 uht=- us=504 ua=192.168.156.2:8080
192.168.156.1 [29/Oct/2026:15:56:55 +0000] "GET /dead/ HTTP/1.1" 504 rt=2.002 urt=2.003 uct=- uht=- us=504 ua=192.0.2.10:8080
192.168.156.1 [29/Oct/2026:15:56:55 +0000] "GET /closed/ HTTP/1.1" 502 rt=0.000 urt=0.000 uct=- uht=- us=502 ua=192.168.156.2:9999
192.168.156.1 [29/Oct/2026:15:56:55 +0000] "GET /app/close HTTP/1.1" 502 rt=0.000 urt=0.001 uct=0.000 uht=- us=502 ua=192.168.156.2:8080
192.168.156.1 [29/Oct/2026:15:57:05 +0000] "GET /app/drip/5/2 HTTP/1.1" 200 rt=10.005 urt=10.004 uct=0.000 uht=0.001 us=200 ua=192.168.156.2:8080
192.168.156.1 [29/Oct/2026:15:57:06 +0000] "GET /app/sleep/5 HTTP/1.1" 499 rt=1.006 urt=1.006 uct=0.001 uht=- us=- ua=192.168.156.2:8080
```

Three rules come out of this table:

- **A 504 is exactly as slow as a timeout.** In this matrix every 502 took one or two milliseconds and every 504 took the configured timeout plus a few milliseconds. If your 5xx latency sits on a round number, it is a timeout. The reverse does not hold: a 502 is only fast when the upstream fails at once.
- **`uct` separates the two 504s.** A number means nginx connected and then waited for the header (slow upstream). A dash means it never connected (unreachable upstream).
- **`proxy_read_timeout` is not a total.** The drip request took 10 seconds under a 3 second read timeout and succeeded, because the [nginx docs](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout) set the timeout "only between two successive read operations, not for the transmission of the whole response." It bounds silence, not duration.

The exact error text depends on the C library nginx was built against. The Alpine image (musl) prints `(110: Operation timed out)`; the Debian `nginx:1.27` image (glibc) prints the string most people search for, `(110: Connection timed out)`, from the same nginx/1.27.5:

```
2026/10/29 15:57:37 [error] 22#22: *1 upstream timed out (110: Connection timed out) while reading response header from upstream, client: 192.168.156.1, server: , request: "GET /app/sleep/5 HTTP/1.1", upstream: "http://192.168.156.2:8080/sleep/5", host: "localhost:18505"
```

Search your logs for `upstream timed out` and the `while ...` clause, not the text in brackets.

## How do you confirm the 504 comes from nginx in Kubernetes?

The lab scenario: a three-node kind cluster running the lab's `shop` app (a load generator calls `frontend`, nginx proxies `/api/` to the `api` Service, the api pings redis). An api release adds a stock-level lookup to every `/items` request: `urllib.request.urlopen("http://192.0.2.10:8080/stock")` with no timeout. 192.0.2.10 is a [TEST-NET-1](https://www.rfc-editor.org/rfc/rfc5737) address that is never routed, standing in for a dependency behind a firewall that drops packets. `/healthz` does not make the call.

The first surprise: the load generator never sees a 504. It waits 3 seconds (`wget -T 3`), so it gives up first:

```shell
kubectl -n shop logs deploy/loadgen --tail=6
```

```

2026-10-29T16:05:17Z GET /api/items -> timeout
2026-10-29T16:05:22Z GET /api/items -> timeout
```

nginx records those as 499 (client closed the request). The one 504 in this output is the scenario's own check request, which waited long enough and got it 60 seconds after it arrived:

```shell
kubectl -n shop logs -l app=frontend --tail=200 --prefix | grep -v healthz | tail -12
```

```
[pod/frontend-76d98597b9-fxhdj/nginx] 10.244.1.15 - - [29/Oct/2026:16:04:27 +0000] "GET /api/items HTTP/1.1" 499 0 "-" "Wget" "-"

[pod/frontend-76d98597b9-fxhdj/nginx] 10.244.1.15 - - [29/Oct/2026:16:04:37 +0000] "GET /api/items HTTP/1.1" 499 0 "-" "Wget" "-"
```

(trimmed: seven more `499` lines through 16:05:32. `kubectl logs -l` prints one pod after the other, so `tail` shows only the second pod.) A client with a longer patience, like a browser, gets the 504:

```shell
kubectl -n shop exec deploy/loadgen -- sh -c "time wget -q -S -O /dev/null -T 90 http://frontend/api/items"
```


One minute is nginx's default `proxy_read_timeout`; the frontend config sets only `proxy_connect_timeout 2s`. If you count only 504s you undercount this incident badly: the 499s are the same failure seen by impatient clients.

Look-alikes: a 504 whose body footer is not nginx came from a hop in front of it (check that hop's timeout and logs). A 502 with `Connection refused` is a Service with no endpoints or a wrong port ([Service has no endpoints](https://www.aurorasre.ai/runbooks/fix-service-no-endpoints-kubernetes), [targetPort mismatch](https://www.aurorasre.ai/runbooks/fix-service-targetport-mismatch-kubernetes)). A 503 from the api itself (`backend unavailable` in the lab app) is the application answering, quickly, with an error.

Scope by path too: in the lab only `/items` failed; `/healthz` on the same pods stayed fast, which already says the problem is inside one code path, not the pod or the network.

## Is the upstream slow, unreachable, or is the timeout too low?

Cheapest check first. Stop at the step that answers it.

**1. Read the `while ...` clause.** `while reading response header from upstream` means connected and waiting (go to step 2). `while connecting to upstream` means the upstream address is not answering at TCP level: from the proxy's pod, connect to the address in the `upstream:` field; a NetworkPolicy, a dead node or a wrong IP drops the SYN (see [NetworkPolicy blocking traffic](https://www.aurorasre.ai/runbooks/fix-networkpolicy-blocking-traffic-kubernetes)). Through a ClusterIP there are two common versions. A port the Service does not publish times out rather than being refused: in our [ConfigMap drift scenario](https://www.aurorasre.ai/runbooks/fix-configmap-change-not-applied-to-all-pods-kubernetes) one frontend pod proxied to `api:8000`, logged `upstream timed out (110: Operation timed out) while connecting to upstream` after its 2 second `proxy_connect_timeout`, and returned 504. Otherwise a pod endpoint is not answering at TCP level. A Service with no endpoints at all refuses instead, which is a fast 502.

**2. Time the upstream directly, bypassing nginx.** From any pod, call the Service or pod on its own port, once on the health path and once on the failing path:

```shell
kubectl -n shop exec deploy/loadgen -- sh -c "time wget -q -O - -T 5 http://api:8080/healthz"
kubectl -n shop exec deploy/loadgen -- sh -c "time wget -q -O - -T 5 http://api:8080/items"
```

```
{"status": "ok"}real	0m 0.00s

wget: download timed out
Command exited with non-zero status 1
real	0m 5.00s
```

If the direct call is also slow, nginx is reporting the truth: the upstream is slow. If the direct call is fast and only the proxied one times out, look at the proxy (wrong upstream, a buffered request body, a hop in between).

**3. Find what the upstream is waiting on.** A slow handler is usually blocked on something outside the process. Socket states inside the pod show it without any tracing tool (Alpine and busybox images ship `netstat`):

```shell
kubectl -n shop exec api-78449dbcf8-6r4qj -- sh -c "netstat -tn | awk 'NR>2{print \$6, \$5}' | sed -E 's/:[0-9]+\$//' | sort | uniq -c"
```

```
    8 CLOSE_WAIT 10.244.1.14
    1 CLOSE_WAIT 10.244.1.15
    5 CLOSE_WAIT 10.244.2.9
   14 SYN_SENT 192.0.2.10
   16 TIME_WAIT 10.244.2.1
    8 TIME_WAIT 10.96.245.99
```

Fourteen connections stuck in `SYN_SENT` to one address: the api is trying to reach 192.0.2.10 and getting nothing back. The `CLOSE_WAIT` rows from 10.244.1.14 and 10.244.2.9 are the two frontend pods: nginx already gave up and closed its side, and the api has not noticed. `SYN_SENT` means an unreachable dependency; many `ESTABLISHED` connections to a database with no `SYN_SENT` means a slow one. Either way, the next place to look is the code that makes that call (here, the new `urlopen` line in the api-code ConfigMap).

**4. Read the upstream's own log, and distrust it.** About two minutes after each request, the api finally wrote (`kubectl -n shop logs api-78449dbcf8-6r4qj --tail=40`, trimmed to these four lines; the first header line of a traceback was interleaved just above them):

```
stock lookup failed: <urlopen error [Errno 110] Operation timed out>
10.244.1.14 "GET /items HTTP/1.0" 200 -
request failed: redis error: [Errno 32] Broken pipe
10.244.1.14 "GET /items HTTP/1.0" 503 -
```

followed by a `BrokenPipeError` traceback. Three things in four lines are misleading. The api logged `200` for a request nginx had already given up on, as a 504 or a 499 (Python's `http.server` logs when it starts the response, not when it is delivered). It then blamed redis, because the lab app's catch-all handler labels every `OSError` a redis error, and the broken pipe to nginx is an `OSError`. And none of this appears until the dependency call gives up: with no timeout set, Python's `urlopen` falls back to the [global default](https://docs.python.org/3/library/urllib.request.html#urllib.request.urlopen), which is no timeout, so the kernel decides. Linux retries a SYN `tcp_syn_retries` times (6 by default), and the [kernel docs](https://www.kernel.org/doc/Documentation/networking/ip-sysctl.rst) put the final timeout at 131 seconds; with the proxy timeout raised to 150 seconds (see the fix section), one request took 2 minutes 13 seconds end to end. During those two minutes the upstream's log is silent about the failing requests.

**5. If the upstream is not broken, compare its normal latency with the timeout.** This is the "timeout too low" case, and it looks different in the access log: some requests to one path succeed just under the timeout and the rest fail exactly at it. Same Docker nginx, `proxy_read_timeout 3s`, test requests that take 2.0 to 3.5 seconds:

```
"GET /app/sleep/2.5 HTTP/1.1" 200 rt=2.501 urt=2.501 uct=0.000 uht=2.501 us=200 ua=192.168.156.2:8080
"GET /app/sleep/2.9 HTTP/1.1" 200 rt=2.900 urt=2.901 uct=0.001 uht=2.901 us=200 ua=192.168.156.2:8080
"GET /app/sleep/3.1 HTTP/1.1" 504 rt=3.005 urt=3.006 uct=0.000 uht=- us=504 ua=192.168.156.2:8080
"GET /app/sleep/3.5 HTTP/1.1" 504 rt=3.002 urt=3.003 uct=0.000 uht=- us=504 ua=192.168.156.2:8080
```

(trimmed: lines cut to the request onward, and the 2.0 second 200 and the two error log lines left out.) The tell is a continuous latency distribution that runs into the timeout and is cut off there, with no change on the upstream side. A slow upstream instead shows a jump: latency was low until a deploy or a dependency event, then everything sits at the timeout. In the lab scenario, every `/items` request failed and none succeeded slowly; that is not a tight timeout.

**6. If the 504 took longer than the timeout, look for retries.** With more than one server in an `upstream` block, nginx's default `proxy_next_upstream error timeout` sends a timed-out request to the next server. Two slow servers, a 3 second read timeout (Debian nginx this time):

```
192.168.156.1 [29/Oct/2026:15:57:45 +0000] "GET /pair/sleep/5 HTTP/1.1" 504 rt=6.007 urt=3.004, 3.004 uct=0.000, 0.001 uht=-, - us=504, 504 ua=192.168.156.2:8080, 192.168.156.4:8080
2026/10/29 15:57:45 [warn] 25#25: *5 upstream server temporarily disabled while reading response header from upstream, client: 192.168.156.1, server: , request: "GET /pair/sleep/5 HTTP/1.1", upstream: "http://192.168.156.4:8080/sleep/5", host: "localhost:18505"
```

(trimmed to the access log line and the second server's warning; the first server's warning at 15:57:42 and both `upstream timed out` lines are left out.) The client waited 6 seconds, both upstreams received the request, and each was marked down for `fail_timeout` (10 seconds by default, [upstream module](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#max_fails)). A plain nginx in front of a ClusterIP sees one address, so it does not retry; ingress-nginx sends to pod IPs directly, and it does (next section).

## What changes with the Kubernetes ingress-nginx controller?

Removing `timeout` from the retry list for this Ingress brought it back to one try:

## What if the readiness probe says context deadline exceeded?

That is the same slowness seen by the kubelet. A Go HTTP client, which the kubelet's probe is, reports its own timeout as `context deadline exceeded`, and a probe's `timeoutSeconds` defaults to 1 ([probe docs](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/#configure-probes)). We ran a copy of the broken api whose readiness probe called `/items` instead of `/healthz`:

```
Readiness probe failed: Get "http://10.244.1.22:8080/items": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

The pod was still `0/1` after 40 seconds. We ran this on one extra Deployment only. Had every api pod used that probe, the Service would have lost its endpoints and the 504s would have turned into fast 502s with `Connection refused` (what the frontend logs in this lab while the api has no ready pods, for example during the selftest's startup), pointing the investigation at the Service layer instead of the dependency. A probe that checks a dependency moves the symptom; keep readiness on a path the pod itself controls.

## How do you fix a 504 Gateway Timeout?

Fix the cause the steps above found. Mitigation and the real fix are separate here, because the quickest mitigation is the wrong one.

**Slow upstream: fix or time-box the call.** In the lab the change was the new dependency call, so the real fix is to revert the api-code ConfigMap change, or to give the call a timeout shorter than the proxy's and a fallback. We applied the second:

```
31c31
<                 with urllib.request.urlopen("http://192.0.2.10:8080/stock") as r:
---
>                 with urllib.request.urlopen("http://192.0.2.10:8080/stock", timeout=1) as r:
```

```shell
kubectl -n shop create cm api-code --from-file=api.py=api-fixed.py --from-file=worker.py=worker.py --dry-run=client -o yaml | kubectl apply -f -
# api-fixed.py is the live api.py with the one-line change; worker.py is unchanged
kubectl -n shop rollout restart deploy/api
```

Risk: a code rollout; a mistake in the patch takes the api down for every path, so watch the rollout. Rollback: apply the previous ConfigMap and restart again, or `kubectl rollout undo deploy/api` if the code lives in the image. After it, the same request returned 200 in one second:

```
{"items": ["kettle", "mug", "teapot"], "stock": {}}real	0m 1.00s
```

Be honest about what that bought: every request still spends one second failing to reach the stock service and returns no stock data. It turns an outage into a degraded feature. The dependency itself (the address, the firewall rule, the service) still needs fixing, and a circuit breaker that stops calling it after repeated failures would remove the one second too.

Expect the old pods to linger during the rollout (`1 old replicas are pending termination` in ours). The lab api runs `python` as PID 1 with no SIGTERM handler, so it ignores SIGTERM and stops only at SIGKILL when the 30 second grace period ends; requests still blocked inside it are cut off then.

**Raising `proxy_read_timeout`: what it actually does.** We set `proxy_read_timeout 150s` on the frontend and sent a patient request:

```
real	2m 13.35s
{"items": ["kettle", "mug", "teapot"], "stock": {}}
```

The 504 is gone and the user now waits 2 minutes 13 seconds for a page with no stock data. Every waiting request holds an nginx connection and an api thread, and clients with shorter timeouts (the load generator, mobile apps, the load balancer in front) still fail, now as 499s and their own timeouts that no 504 alert counts. Raise the timeout only when the endpoint is legitimately slow and you have measured it: set it in the one `location` (or, on ingress-nginx, the one Ingress) that needs it, a little above that endpoint's measured p99, never server-wide. Risk: longer-held connections and workers under load. Rollback: remove the line and reload nginx (`nginx -s reload`, or restart the pods when the config is a mounted ConfigMap, as here).

**Unreachable upstream (`while connecting`).** Fix the address or the network path: the Service's endpoints, the NetworkPolicy, the node. Lowering `proxy_connect_timeout` (ingress-nginx defaults to 5 seconds; stock nginx to 60) only makes the failure faster, which is worth doing so a dead peer costs seconds, not a minute, but it is not a fix.

**Retries multiplying the wait.** On ingress-nginx, `nginx.ingress.kubernetes.io/proxy-next-upstream: "error"` stops retrying timeouts for one Ingress, as shown above; `proxy-next-upstream-timeout` caps the total time spent retrying instead. Keep timeout retries only if the backend's work is safe to run twice. nginx does not retry non-idempotent methods such as POST once the request has been sent ([proxy_next_upstream](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_next_upstream)), but GETs that write are common. Risk of the annotation: a timeout on one pod is no longer hidden by a retry on a healthy one, so a single slow pod now shows as 504s. Rollback: `kubectl -n shop annotate ingress api nginx.ingress.kubernetes.io/proxy-next-upstream-` removes it.

## How do you verify the fix?

Pass condition: on the failing path, a request through the proxy returns 200 well under the timeout, the client's own log shows 200s, and no new `upstream timed out` line appears for at least ten minutes of normal traffic (longer than one deploy cycle and the 131 second connect timeout). In the lab, the load generator's last five lines, starting 10 seconds after we began applying the fix at 16:09:38:

```shell
kubectl -n shop logs deploy/loadgen --tail=5
```

```
2026-10-29T16:09:48Z GET /api/items -> 200
2026-10-29T16:09:51Z GET /api/items -> 200
2026-10-29T16:09:54Z GET /api/items -> 200
2026-10-29T16:09:57Z GET /api/items -> 200
2026-10-29T16:10:00Z GET /api/items -> 200
```

Then confirm there is nothing left hanging inside the upstream: `netstat -tn` in a new api pod should show no pile of `SYN_SENT` or `CLOSE_WAIT`. The fixed pods still logged `stock lookup failed: <urlopen error timed out>` on every request, which is the expected degraded state, not a pass for the dependency.

## How do you prevent it?

**Alert on the timeout before it fires, and count 499s with 504s.** With ingress-nginx's Prometheus metrics (`nginx_ingress_controller_requests` carries `status`, `namespace`, `ingress` and `service` labels in v1.15.1, [source](https://github.com/kubernetes/ingress-nginx/blob/controller-v1.15.1/internal/ingress/metric/collectors/socket.go)):

```
sum by (namespace, ingress) (rate(nginx_ingress_controller_requests{status=~"504|499"}[5m]))
/
sum by (namespace, ingress) (rate(nginx_ingress_controller_requests[5m]))
> 0.01
```

We did not run this query against a live Prometheus in the lab; it is built from the metric and label names in the controller source. If the controller runs with `--report-status-classes`, the label holds `4xx` and `5xx` instead of codes and this regex matches nothing. For latency, the histograms (`nginx_ingress_controller_header_duration_seconds` and the others) use Prometheus' default buckets, whose largest finite bucket is 10 seconds, so a "p99 near the 60 second timeout" alert cannot be computed until you add buckets with the controller's `--time-buckets` flag. On plain nginx, add `$request_time`, `$upstream_connect_time` and `$upstream_header_time` to the log format, as in our table; without them you cannot tell the three causes apart after the fact.

**Guardrail: every timeout shorter than the one above it.** The client's timeout should be longer than the proxy's, the proxy's longer than the upstream's own request budget, and every outbound call inside the upstream should have a timeout shorter than that budget. The lab failure is the inversion: the only finite timeout on the path was nginx's 60 seconds, so nginx was the one to give up.

**Test.** In CI, run the service with each dependency pointed at a blackholed address (192.0.2.0/24 drops packets on our network; check that yours drops rather than rejects it) and assert that a request still returns within your budget. We have not built that test; the timed requests above are its manual version, and they separate the lab's broken release (no answer in 60 seconds) from the fixed one (200 in one second).

## Common mistakes

- **Raising `proxy_read_timeout` as the fix.** Shown above: the 504 became a 2 minute 13 second 200 with missing data. It is also listed as a wrong answer in the scenario's grading.
- **Looking for the 504 in the application's logs.** The application never sends it. Ours logged `200` and then `503` for requests nginx had already answered with 504 or logged as 499.
- **Believing the upstream's error message.** The lab api blamed redis for the broken pipe to nginx. redis was fine the whole time.
- **Counting only 504s.** Most failed requests in the lab were 499s, because the load generator's 3 second timeout is shorter than nginx's 60.
- **Restarting pods.** New pods run the same code and hang on the same call.
- **Reading every 504 as a slow backend.** `while connecting to upstream` against a ClusterIP can be a port the Service does not publish, with a perfectly healthy backend behind it. Read the `while ...` clause first.
- **Ignoring retries.** On ingress-nginx, a 504 at three times the timeout means each slow request ran three times on the backend, which can be what is making it slow.

## Questions people ask

**What does 504 Gateway Timeout mean?**

A proxy or gateway, such as nginx, an ingress controller or a load balancer, waited for the server behind it and gave up before a response arrived, so it answered the client with 504 itself. The application did not send the 504; in nginx the error log line upstream timed out ... while reading response header from upstream or while connecting to upstream says which wait ran out.

**What is the difference between 502 and 504 in nginx?**

A 502 means the upstream answered badly or not at all: connect() failed (111: Connection refused) or upstream prematurely closed connection. A 504 means nginx timed out waiting, so it arrives at proxy_read_timeout or proxy_connect_timeout. In our tests every 502 took one or two milliseconds and every 504 took the configured timeout plus a few milliseconds.

**How do I fix 504 Gateway Timeout in nginx?**

Find what the upstream is waiting on and fix that: time a request to the upstream directly, check its connections (netstat -tn in the pod) and recent changes. In our lab the cause was a new dependency call with no timeout; giving it a 1 second timeout and a fallback turned a 60 second 504 into a 1 second 200. Raise proxy_read_timeout only for an endpoint that is legitimately slow, in that location only.

**Should I just increase proxy_read_timeout?**

Usually not. When we raised it from 60 to 150 seconds the 504 disappeared and users waited 2 minutes 13 seconds for a response with missing data, while every waiting request held an nginx connection and an upstream thread. Raise it only when you have measured that the endpoint's normal latency is above the current value.

**Why does nginx say Operation timed out instead of Connection timed out?**

The text in brackets is the C library's message for errno 110. nginx built against glibc (the Debian nginx image) prints (110: Connection timed out); nginx built against musl (the Alpine image) prints (110: Operation timed out). Both come from the same nginx/1.27.5 and mean the same timeout.

**Why is my 504 taking longer than proxy_read_timeout on ingress-nginx?**

ingress-nginx retries timeouts on other pods by default (proxy-next-upstream error timeout, proxy-next-upstream-tries 3). With a 10 second read timeout our request took 30 seconds and hit one pod twice. The annotation nginx.ingress.kubernetes.io/proxy-next-upstream: "error" brought it back to one 10 second try.

**What does context deadline exceeded mean in a readiness probe?**

The kubelet's HTTP probe timed out waiting for the response headers; timeoutSeconds defaults to 1. If the probe calls a slow path, the pod goes NotReady and leaves the Service's endpoints, which turns 504s into 502s. Keep readiness probes on a path that does not call slow dependencies.
