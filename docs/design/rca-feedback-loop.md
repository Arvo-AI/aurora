# RCA Feedback Loop — Design

**Status:** Draft
**Goal:** Close the loop between Aurora's RCA conclusion and what the humans actually
found and fixed, so that Aurora (a) knows when it was wrong, (b) stores a lesson, and
(c) retrieves prior resolutions on the next similar incident.

---

## 1. Problem

Aurora today is an **open loop**. It investigates, publishes a conclusion, and then never
learns what happened next.

Three independent breaks:

### 1.1 Aurora never ingests the human resolution

`resolved_at` is written in exactly two places in the entire codebase:

- `server/routes/aws/cloudwatch_tasks.py:186` — automatic, from an `OK` alarm transition
- `server/routes/incidents_routes.py:1211-1212` — manual dashboard PATCH

Every other connector either drops the resolve event at an event gate or stores it in the
provider events table without touching `incidents`. Consequences:

- MTTR (`server/routes/metrics_routes.py:70-75` requires `resolved_at IS NOT NULL`)
  effectively only measures CloudWatch plus manually-closed incidents.
- The human's closing narrative — the single highest-value training signal we have — is
  never persisted anywhere.

Per-connector state:

| Connector | Resolve event handled? | `status` | `resolved_at` | Human resolution text upstream | Client method exists? |
|---|---|---|---|---|---|
| incident.io | ❌ dropped at `_NEW_INCIDENT_EVENTS` (`routes/incidentio/tasks.py:567-581`, gate `:817`) | ❌ | ❌ | ✅ richest: `incident_updates`, `follow_ups`, `postmortem_document_url` | ✅ `get_incident_updates` (`incidentio_routes.py:107`) |
| PagerDuty | ✅ status synced (`routes/pagerduty/tasks.py:642-665`) | ✅ | ❌ **missing** | ✅ `resolve_reason`, `/notes`, `/log_entries` | ⚠️ `_request` only (`pagerduty_helpers.py:55`); writes notes, never reads |
| Jira | ❌ create-only (`routes/jira/jira_routes.py:393-396`) | ❌ | ❌ | ✅ `fields.resolution` + `resolutiondate`, comments, changelog | ✅ `get_issue` (`jira_connector/client.py:157`) |
| Opsgenie / JSM | ❌ `("create","create alert")` only (`routes/opsgenie/tasks.py:128-130`) | ❌ | ❌ | ✅ close `note` via `/notes` + `/logs` | ✅ `get_alert_notes` (`opsgenie_routes.py:102`) |
| Grafana | ⚠️ detected but no-op (`routes/grafana/tasks.py:28-32`, `:299-311` then `continue`) | ❌ | ❌ | ⚠️ annotations / silence comments only | ❌ no client class at all |
| Sentry | ❌ worse — `issue.resolved` opens a **new** incident (`routes/sentry/tasks.py:174,228`; unique idx `db_utils.py:686`) | ❌ | ❌ | ✅ `/activity/`, `/notes/`, `statusDetails.inCommit` | ⚠️ `get_issue` only |
| New Relic | ❌ `VALID_ISSUE_STATES` declared but unenforced (`routes/newrelic/config.py:7`) | ❌ | ❌ | ✅ `closedBy` / closing reason, annotations | ⚠️ needs new NerdGraph query |
| Dynatrace | ❌ `State` stored, never branched (`routes/dynatrace/tasks.py:87`) | ❌ | ❌ | ✅ `recentComments`, `closeReason` | ❌ thinnest client |
| BigPanda | ❌ `event_type="incident.resolved"` synthesized then ignored (`routes/bigpanda/tasks.py:122-123`) | ❌ | ❌ | ✅ incident comments | ⚠️ `get_incident` only |
| Elastic | ⚠️ `recovered` short-circuits cleanly (`routes/elastic/tasks.py:304-317`) but only bumps `updated_at` | ❌ | ❌ | ⚠️ Cases API only | ❌ no Cases support |
| Datadog | ❌ no event gate at all (`routes/datadog/tasks.py:49-69` always True) | ❌ | ❌ | ⚠️ Incident Mgmt `fields.resolution` | ✅ `list_incidents` (unused) |
| CloudWatch | ✅ **reference implementation** (`cloudwatch_tasks.py:145-205`) | ✅ | ✅ | ❌ machine-generated only | n/a |
| Netdata / Coroot / ThousandEyes / Splunk | ❌ | ❌ | ❌ | ❌ nothing worth chasing | — |

Note the irony: the connector with the best lifecycle handling (CloudWatch) has the least
human text to gain, and the one with the richest text (incident.io) drops the event.

Also: only 5 of 14 ingesting connectors write `incident_lifecycle_events` at all
(PagerDuty, Grafana, Datadog, Jira, CloudWatch) — the rest have an empty audit timeline.

### 1.2 Postmortems are a write-only dead end

Postmortems live in `artifacts` with `category='postmortem'` (`db_utils.py:1317-1331`),
fully versioned (`artifact_versions`, `:1333-1348`), generated by a background agent
(`services/actions/postmortem_action.py:63-167`) on incident resolve
(`services/actions/system_actions.py:69-77`).

Nothing in the RCA path ever queries them:

- **No `search_postmortems` tool exists.**
- `get_postmortem` (`agent/tools/postmortem_tool.py:31-84`) requires an `incident_id` you
  already know — no search, no filter.
- `postmortem_list` (`agent/tools/introspection_tools.py:777-810`) selects metadata only —
  **it never selects `content`** (`:784-798`), so it cannot surface a past root cause.
- `postmortem/SKILL.md:11` sets `rca_priority: 90` — nearly last. The intended
  "look for past postmortems" step points at *external* stores instead
  (`confluence/SKILL.md:38`, `notion/SKILL.md:305`). Teams that don't export to
  Confluence/Notion have an invisible postmortem corpus.

Worse: `artifact_versions.source='pre_edit'` snapshots (`postmortem_routes.py:263-269`)
are literal, free, human-authored proof of what Aurora got wrong — and **nothing ever
reads them.**

### 1.3 No ground truth, so no reflection

- **No confidence column.** `incidents` has no `root_cause` or `confidence` field
  (`db_utils.py:768-792`). CONFIRMED / LIKELY / INCONCLUSIVE is prose *inside*
  `aurora_summary` (`prompt/rca_sections/conclusion_gate.md:19-21`) — never queryable.
  The only structured signal is per-sub-agent `rca_findings.self_assessed_strength`
  (`db_utils.py:1376`), which is self-assessed at write time, not validated.
- **No feedback UI.** Zero matches across `client/src` for thumbs / accept / reject /
  correct / helpful on an RCA. `incidents_routes.py:1206-1240` PATCH accepts only
  `status`, `aurora_status`, `aurora_summary`, `active_tab`.
- **The memory collector actively forbids learning from RCA.**
  `services/memory/collector.py:77`: *"DO NOT save obvious/generic knowledge the assistant
  generated (only save facts the USER provided)"*. So a wrong conclusion is neither stored
  nor corrected — it evaporates.
- The only existing epistemic guard is a warning, not a mechanism:
  `skills/core/memory.md:23` — *"NEVER blindly trust 'learned' memories as root causes."*

### 1.4 What partially works today

- **Incident Index** (`services/memory/incident_index.py`) — one org artifact, one line per
  incident, cause-focused synopsis capped at 160 chars (`:28`), written at RCA completion
  (`chat/background/summarization.py:889-937`). But `read_index` is called from **exactly
  one place** (`services/correlation/recurrence_agent.py:359-360`) — the main RCA prompt
  never sees it.
- **Recurrence agent** (`recurrence_agent.py:645-732`) — good architectural template:
  read-only toolset (`EXCLUDED_TOOL_NAMES:67-110`), MCP fails closed (`:136-152`),
  server-side id validation (`_clamp_claimed_id:382-411`), `off`/`shadow`/`live` modes
  (`recurrence_config.py:46-60`), verdicts persisted with a unique
  `(incident_id, decision_point)` for retry idempotency (`db_utils.py:1401-1424`).
  **We should copy this shape.**
- **Slack** — scopes already permit reading public/private history and threads
  (`connectors/slack_connector/oauth.py:28-44`), and `get_channel_history` /
  `get_thread_replies` exist (`agent/tools/slack_tool.py:153`, `:246`). But there is **no
  scheduled read-back**: `celery_config.py:162-191` has zero Slack beat entries. An RCA
  thread's resolution is only consumed if a human @mentions Aurora
  (`routes/slack/slack_events.py:217-218`, `limit=10`) or someone manually triggers
  Generate Postmortem (which relies purely on prompt compliance with an unbounded time
  window, `postmortem_action.py:39-45`).
- Only `incidents.slack_message_ts` is persisted (`db_utils.py:784`) — there is **no
  `slack_channel_id` column**; the channel is re-derived from an org preference
  (`slack_notification_service.py:42-66`).

### 1.5 The loop, as it stands

```
RCA run ──> aurora_summary (free text, no confidence column)
   │            ├──> recurrence_verdicts + fold
   │            ├──> Incident Index line (160-char synopsis) ──┐
   │            └──> extract_memories_from_session ────────────┤ (forbidden from
   │                                                           │  saving RCA output)
   ├──> [on resolve] generate_postmortem                       │
   │        └──> artifacts + versions ──> human edit ──> ✗ DEAD END
   │                                                           │
   └──<── next RCA reads: Incident Index (recurrence agent only) ◄┘
                          memory injector (≤5 entries, ≤4KB)
                          list_incidents (agent-initiated)
                          Confluence / Notion (external copies only)

   Human's actual fix ──────────────> ✗ NEVER INGESTED
```

## 2. Phase 1 — Capture ground truth

**Goal:** one normalized, queryable record of *what the humans said fixed it*, per incident,
regardless of source. Nothing else in this doc works without it.

Priority order (per product decision): **human-authored resolve notes from any platform
first**, then comms channels, then inferred sources.

### 2.1 New table: `resolution_reports` (write-many, one row per capture)

Rather than one column on `incidents`, use an append-only evidence table so multiple
sources can contribute and we keep provenance.

```sql
CREATE TABLE IF NOT EXISTS resolution_reports (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    incident_id       UUID NOT NULL REFERENCES incidents(id) ON DELETE CASCADE,
    org_id            VARCHAR(255) NOT NULL,
    user_id           VARCHAR(255) NOT NULL,

    -- provenance
    source            VARCHAR(32)  NOT NULL,   -- 'incidentio'|'pagerduty'|'jira'|'opsgenie'|'slack'|'human_ui'|'github'
    source_ref        VARCHAR(255),            -- upstream id (note id, update id, message ts, PR url)
    captured_by       VARCHAR(20)  NOT NULL,   -- 'connector'|'agent'|'human'
    author_external   VARCHAR(255),            -- upstream author handle (NOT an email)

    -- payload
    resolution_text   TEXT NOT NULL,           -- verbatim human narrative
    actual_root_cause TEXT,                    -- extracted/normalized, nullable
    fix_type          VARCHAR(32),             -- 'rollback'|'config'|'code'|'scale'|'restart'|'upstream'|'no_action'|'unknown'
    fix_ref           TEXT,                    -- PR/commit/runbook url
    confidence        VARCHAR(16),             -- 'verbatim'|'extracted'|'inferred'

    raw_payload       JSONB,
    occurred_at       TIMESTAMP,               -- when the human wrote it
    created_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE (org_id, source, source_ref)        -- webhook-retry idempotency
);
CREATE INDEX idx_resolution_reports_incident ON resolution_reports(incident_id);
```

- **Must be added to `rls_tables`** in `server/utils/db/db_utils.py:1601`-ish alongside
  `incidentio_alerts`. It is per-org incident data.
- `UNIQUE (org_id, source, source_ref)` + `ON CONFLICT DO NOTHING` makes Celery retries safe
  (same trick as `recurrence_verdicts`' unique `(incident_id, decision_point)`).
- `confidence = 'verbatim'` is the gold tier — a human literally typed this into the
  incident tool. `'extracted'` = LLM pulled it out of a Slack thread. `'inferred'` = we
  guessed from a linked PR.
- Per the no-real-production-data rule: `author_external` stores the upstream *handle*, and
  must never be logged. `resolution_text` is customer content — never log it, never put it
  in a test fixture.

### 2.2 Fix the lifecycle first (small, independently shippable)

These are prerequisites — without a real resolve transition there is no trigger to hang
capture off.

Adopt `cloudwatch_tasks.py:145-205` as the canonical shape and factor it into a shared
helper so we stop reimplementing it per connector:

```python
# server/services/incidents/resolution.py  (new)
def mark_incident_resolved(cursor, conn, *, incident_id, org_id, user_id,
                           previous_status, source, resolved_at=None) -> bool:
    """Flip status->'resolved', stamp resolved_at, write a lifecycle row.

    Idempotent: no-ops when the incident is already resolved/closed so retried
    webhooks don't duplicate lifecycle rows.
    """
```

Then, in priority order:

1. **PagerDuty** — smallest possible fix: add `resolved_at` to the existing
   `ON CONFLICT DO UPDATE` at `routes/pagerduty/tasks.py:642-665`. It already syncs status
   and writes a `resolved` lifecycle row (`:730`); it just drops the timestamp.
2. **Grafana** — the transition is 90% built. At `routes/grafana/tasks.py:299-311` it
   already resolves the fingerprint back to the original incident and inserts an
   `incident_alerts` row with `correlation_strategy='resolved_webhook'`, then `continue`s.
   Call `mark_incident_resolved` instead of falling through.
3. **incident.io** — add a `_RESOLVED_INCIDENT_EVENTS` frozenset next to
   `tasks.py:567-581` and branch **before** the `event_type not in _NEW_INCIDENT_EVENTS`
   early return at `:817-821`. Update the setup instructions at
   `incidentio_routes.py:392-398` to ask for the status-update topic.
4. **Elastic** — `recovered` already short-circuits correctly
   (`routes/elastic/tasks.py:304-317`); add the resolve call.
5. **Opsgenie** — the create-only gate at `routes/opsgenie/tasks.py:128-130` must grow a
   `Close` branch. Note `opsgenie_routes.py:688,696` *already tells users to subscribe to
   `Close`*, so those webhooks are arriving and being thrown away today.
6. **Sentry** — actual bug to fix: `issue.resolved` currently creates a **new incident**.
   Gate on `action` (it's already read at `routes/sentry/tasks.py:174`) and route resolved
   actions to the resolve path instead of the create path.
7. **New Relic** — enforce the already-declared `VALID_ISSUE_STATES`
   (`routes/newrelic/config.py:7`) on the webhook path.
8. **Jira / Datadog / BigPanda / Dynatrace** — add event gates, then resolve handling.

### 2.3 Capture human resolve notes (Tier 1 — `confidence='verbatim'`)

On the resolve transition, enqueue `capture_resolution.delay(incident_id, source)`. Per
connector:

| Source | Fetch | Notes |
|---|---|---|
| **incident.io** | `get_incident_updates()` (already exists, `incidentio_routes.py:107`) + new `list_follow_ups()`, `get_incident()` for `postmortem_document_url` | `incidentio_tool.py:275-288` already normalizes updates to `{message, updater, new_status, created_at}` — reuse it verbatim. Take the last few updates before close as the resolution narrative. |
| **PagerDuty** | new `get_incident(id)` → `resolve_reason`, `get_notes(id)`, optionally `get_log_entries(id)` for the `resolve_log_entry` | `_request` already exists (`pagerduty_helpers.py:55`); `PD_READ_ONLY_ROLES` (`:31`) shows the permission model is understood. |
| **Jira** | existing `get_issue` with `fields=resolution,resolutiondate` + new `get_comments()` | Nearly free — `fields.resolution` comes back with the right `fields` param. |
| **Opsgenie / JSM** | `get_alert_notes()` / `get_alert_logs()` — already wrapped and parallelized in `opsgenie_tool.py:85-120` | Harvest the `Close` log entry's note + author. |
| **Dynatrace** | new `get_problem(id)` → `closeReason`, `recentComments` | Cleanest upstream story, thinnest existing client. |
| **Sentry** | new `get_issue_activity(id)` → `set_resolved_*` + `statusDetails.inCommit` | `inCommit` gives us `fix_ref` for free. |
| **BigPanda / New Relic / Datadog** | new client methods | Lower priority. |

Also fix an adjacent bug: incident.io API v2 nests status as an object, but we read a flat
`incident.get("status")` at `routes/incidentio/tasks.py:518` and
`agent/tools/incidentio_tool.py:130`. Should be `incident_status.category`. Current test
fixtures use a synthetic flat `"status": "open"` (`test_alert_rca.py:254`), so this is
uncovered.

**Design rule:** capture is *verbatim first*. Store `resolution_text` exactly as written
with `confidence='verbatim'` and leave `actual_root_cause` NULL. Normalization is Phase 2's
job — we never want the ingestion path to lose the original words.

### 2.4 Capture from comms threads (Tier 2 — `confidence='extracted'`)

Slack is the only real comms connector. Google Chat exists but is notify/reply-only with no
agent tools and a `chat.bot` scope that usually can't read. Teams and Discord don't exist.

Two prerequisites:

1. **Persist the channel.** Add `incidents.slack_channel_id`. Today only
   `slack_message_ts` is stored (`db_utils.py:784`) and the channel is re-derived from the
   org preference `slack_incidents_channel_id`
   (`slack_notification_service.py:42-66`) — which breaks the moment the team-routing agent
   posts somewhere else (`slack_team_routing.py:131-190` explicitly can).
2. **Add a scheduled sweep.** `celery_config.py:162-191` has zero Slack beat entries. Add
   `harvest_incident_threads`, hourly, scanning incidents resolved in the last N hours that
   have a `(slack_channel_id, slack_message_ts)` pair and no `source='slack'`
   resolution report.

The task calls `get_thread_replies` (`slack_tool.py:246`) — bounded, deterministic, with an
explicit window from `alert_fired_at` to `resolved_at` — and runs a **small extraction LLM**
that answers one question: *did a human state how this was fixed, and if so, verbatim what
did they say?* It must be allowed to answer "no". Output is written with
`confidence='extracted'`.

Deliberately **not** doing the postmortem action's approach of letting the agent freestyle
`get_channel_history` over an unbounded window (`postmortem_action.py:39-45`) — that's
unpredictable and not guaranteed to run at all.

Note: we have no `search:read` scope (`connectors/slack_connector/oauth.py:28-44`), so no
workspace-wide search. Thread-scoped reads only.

### 2.5 Human input in Aurora (Tier 0 — highest quality)

A small UI affordance on the incident: **"What actually fixed this?"** — a free-text box
plus an optional `fix_type` select and a PR link. Writes `source='human_ui'`,
`captured_by='human'`, `confidence='verbatim'`.

This is the cheapest path to high-quality ground truth and doesn't depend on any connector.
Ship it alongside 2.3.

Route: `POST /api/incidents/<id>/resolution`, `@require_permission("incidents", "write")`.
Client goes through the proxy per the boundary rules — never straight to Flask.

### 2.6 Inferred sources (Tier 3 — later)

- **Linked PR/commit.** Sentry's `statusDetails.inCommit` and incident.io follow-ups often
  carry one. GitHub connector could resolve it to a diff → strong `fix_type` signal.
- **Deploy correlation.** We already ingest `jenkins_deployment_events` /
  `spinnaker_deployment_events`. A deploy immediately preceding resolution is weak evidence
  of a rollback fix.

Both are `confidence='inferred'` and should never outrank a verbatim human note.

## 3. Phase 2 — Reflection agent

**Goal:** compare Aurora's conclusion to ground truth, record a verdict, and write a lesson
that actually changes future behavior.

### 3.1 Trigger

New Celery task `reflect_on_rca(incident_id)`, enqueued when a `resolution_reports` row
lands **and** the incident has a completed RCA (`aurora_status='complete'`,
`aurora_summary` non-empty). Debounced — wait for a short quiet period so a burst of
captures (incident.io update + Slack thread + human UI) produces one reflection, not three.

If `aurora_summary` is empty or the RCA never ran, skip. Nothing to reflect on.

### 3.2 Architecture — copy the recurrence agent

`server/services/correlation/recurrence_agent.py` is the right template and should be
mirrored closely rather than reinvented:

| Property | Recurrence agent | Reflection agent |
|---|---|---|
| Entry point never raises | `run_recurrence_check:645-732` | same contract — a failed reflection must never affect the incident |
| Read-only toolset | `EXCLUDED_TOOL_NAMES:67-110` + write-verb prefix filter `:113-122` | same, plus allow exactly one write: `write_memory` for the lesson (or better: return the lesson and have the *caller* write it, keeping the agent itself read-only) |
| MCP fails closed | `:136-152` | same |
| Bounded | `MAX_TURNS=15`, 120s | `MAX_TURNS≈12`, 120s |
| Modes | `off`/`shadow`/`live` via `RECURRENCE_DETECTION_MODE` (`recurrence_config.py:46-60`) | `RCA_REFLECTION_MODE`, **default `shadow`** — record verdicts, write no memories, until we trust it |
| Server is the authority | `_clamp_claimed_id:382-411` | validate that any cited incident id is real and RLS-visible before persisting |
| Idempotent persistence | unique `(incident_id, decision_point)` | unique `(incident_id, resolution_report_id)` |

**Strong preference:** make the agent itself fully read-only and return a structured
verdict; the Celery caller does the single memory write. That keeps the blast radius of a
misbehaving reflection agent to "wrote a row in its own table."

### 3.3 New table: `rca_verdicts`

```sql
CREATE TABLE IF NOT EXISTS rca_verdicts (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    incident_id           UUID NOT NULL REFERENCES incidents(id) ON DELETE CASCADE,
    resolution_report_id  UUID REFERENCES resolution_reports(id) ON DELETE SET NULL,
    org_id                VARCHAR(255) NOT NULL,
    user_id               VARCHAR(255) NOT NULL,

    verdict               VARCHAR(20) NOT NULL,  -- 'correct'|'partial'|'wrong'|'unverifiable'
    reasoning             TEXT,                  -- why the agent judged it that way
    aurora_claim          TEXT,                  -- what Aurora concluded (snapshot)
    actual_cause          TEXT,                  -- what it really was (snapshot)
    missed_signal         TEXT,                  -- evidence that WAS available and ignored
    failure_mode          VARCHAR(40),           -- see taxonomy below
    lesson_written        BOOLEAN DEFAULT FALSE,
    lesson_memory_title   VARCHAR(500),

    mode                  VARCHAR(10) NOT NULL,  -- 'shadow'|'live'
    model                 VARCHAR(100),
    elapsed_ms            INTEGER,
    created_at            TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE (incident_id, resolution_report_id)
);
```

RLS-protected. Snapshotting `aurora_claim` / `actual_cause` matters because both source
texts are editable after the fact.

### 3.4 Failure-mode taxonomy

Free-text lessons are hard to aggregate. A closed vocabulary makes Phase 4 measurement
possible and gives the lesson a shape:

| `failure_mode` | Meaning |
|---|---|
| `symptom_as_cause` | Reported a downstream symptom as the root cause |
| `stopped_too_early` | Had the right thread, didn't pull it |
| `wrong_service` | Blamed the wrong component |
| `missing_data_source` | The answer lived in a connector we don't have or didn't query |
| `stale_memory` | A `learned` memory led it astray (the risk `memory.md:23` warns about) |
| `correlation_error` | Attached to the wrong incident / wrong recurrence fold |
| `deploy_blindspot` | A deploy/config change was the cause and we didn't check |
| `insufficient_evidence` | Correctly inconclusive — **not a failure** |

`insufficient_evidence` paired with `verdict='wrong'` is different from
`verdict='inconclusive'` — an honest "I don't know" that turned out to have a knowable
answer is a retrieval problem, not a reasoning problem. Track them separately.

### 3.5 Verdict semantics

The prompt must be biased the way the recurrence prompt is biased
(`recurrence_prompt.md:18`), but in the opposite direction. Recurrence defaults to "new"
because a wrong fold hides a real incident. Reflection should default to **`unverifiable`**,
because a wrong "correct" verdict inflates our accuracy metric and a wrong "wrong" verdict
poisons memory with a bogus lesson.

- `correct` — Aurora named the same causal mechanism the humans fixed.
- `partial` — right component or right layer, wrong mechanism; or right cause but missed a
  material contributing factor.
- `wrong` — Aurora named a different mechanism, or named a symptom.
- `unverifiable` — the resolution note is too thin to judge ("fixed", "restarted it",
  "see thread"). **This will be the majority case early on**, and that's fine — it's an
  honest signal about resolve-note quality, and worth surfacing in Phase 4.

Match on *causal mechanism*, not wording — same standard as
`recurrence_prompt.md:5`.

### 3.6 The lesson

Only written when `verdict IN ('partial','wrong')` and mode is `live`.

The lesson must be **actionable and generalizable**, not a restatement of the incident.
Bad: "INC-123 was actually a connection pool exhaustion." Good: "For <service>, p99 latency
spikes with flat error rate have twice been pool exhaustion, not the downstream dependency
the traces implicate — check pool saturation metrics before blaming downstream."

Written as `category='learned'` via the existing `write_memory` path
(`agent/tools/memory_tool.py:228`), which gives us versioning and the nightly
`memory_consolidation` grooming (`services/actions/system_actions.py:88-96`) for free.

**Two things must change in memory for this to work:**

1. `services/memory/collector.py:77` currently forbids saving assistant-generated
   knowledge. That rule exists for good reason in the *conversation* collector — but the
   reflection path is different: its conclusions are **validated against ground truth**.
   Keep the collector rule as-is; the reflection agent writes through its own path, and
   the distinction should be documented so nobody "unifies" them later.
2. `skills/core/memory.md:23` warns never to trust `learned` memories as root causes.
   That guard should stay, but reflection-derived lessons should be **marked as
   ground-truth-validated** in their content so the RCA agent can weight them higher than
   an unvalidated pattern. Consider a convention like a `Validated against: INC <id> resolution`
   line in the entry body, since there is no structured tag column today (memory is scoped
   org-only — see §5.2).

Prefer `append_to_memory` with `skip_if_contains` (which re-checks the idempotency marker
under a `FOR UPDATE` lock, `memory_tool.py:351-371`) over creating a new entry per
incident — otherwise we'll generate hundreds of near-duplicate `learned` entries and blow
the 200-line memory index cap (`index_builder.py`, `MAX_INDEX_LINES`).

### 3.7 Failure handling

Fail open, always. A reflection timeout, an LLM error, or a malformed verdict must leave
the incident, the postmortem, and memory untouched. Log the failure, no retry (match
`collector.py`'s `max_retries=0` posture — a stale reflection is worthless).

## 4. Phase 3 — Retrieval (the payoff)

Ground truth and verdicts are worthless if the next RCA can't see them. Four changes.

### 4.1 `search_postmortems` agent tool

The missing tool. Searches `artifacts` where `category='postmortem'` by content, scoped to
the org via RLS.

- **Start keyword/regex**, matching `grep_memories`' existing approach (`content ~* %s`
  inside a `SAVEPOINT` with an `ILIKE` fallback for invalid regex,
  `agent/tools/memory_tool.py:552-599`). Cheap, no new infra.
- **Then consider embeddings.** `services/correlation/embedding_client.py:22-158` is already
  provider-agnostic (OpenAI/Google/Bedrock via `EMBEDDING_MODEL` as `provider/model`) with a
  Jaccard fallback when unconfigured. Reuse it — do not build a second embedding path.
  Note `recurrence_agent.py:358` deliberately avoids embeddings for determinism; that's a
  different tradeoff than semantic search over a document corpus, and both can coexist.
- Return the **Root Cause + Resolution + Lessons Learned sections**, not the whole document.
  Postmortems can be long and the RCA context budget is finite.
- Must be registered into the RCA toolset in `agent/tools/cloud_tools.py`, and the
  `postmortem/SKILL.md:11` `rca_priority: 90` must drop dramatically — searching our own
  postmortem corpus should happen *before* reaching out to Confluence/Notion
  (`rca_priority` 1 and 4 respectively), not after.

Also fix `postmortem_list` (`introspection_tools.py:784-798`) to optionally include a
content excerpt, or deprecate it in favor of the new tool.

### 4.2 Inject the Incident Index into the main RCA prompt

`read_index` (`incident_index.py:391-433`) is currently called from exactly one place
(`recurrence_agent.py:359-360`). The main RCA prompt never sees it, even though
`prompt/rca_sections/investigation.md:3` explicitly tells the agent to "start with history."

Inject it — trimmed well below the 40k `INDEX_INJECTION_CHAR_BUDGET` (`incident_index.py:36`)
for the RCA path, probably filtered to the affected service plus recent entries. This turns
"start with history" from an instruction the agent may or may not act on into data it
already has.

### 4.3 Surface resolution + verdict on past incidents

When the agent calls `get_incident` / `list_incidents` on a past incident, the response
should include the **actual resolution** and, if present, the **verdict on Aurora's prior
conclusion**.

This is the single highest-leverage change in the whole document. It means:
- "We've seen this before and here's what actually fixed it" becomes available.
- `investigation.md:3`'s framing — *"A prior conclusion is a hypothesis to disprove with
  fresh evidence, never a verdict"* — gets sharper: a conclusion we know was `wrong` should
  be presented as such, and a conclusion validated as `correct` can be trusted more.

Concretely: never resurface a prior conclusion without its verdict attached, when one exists.

### 4.4 Weight memory by validation

`services/memory/injector.py`'s LLM selector picks ≤5 entries from title + category +
`description[:150]` (`:181-192`). Reflection-derived lessons should be discoverable — which
means the lesson's `description` field matters enormously (`memory.md:70-71` already flags
this). The reflection agent must write a good description, not just good content.

Stretch: if an entry's lesson has since been contradicted by a later verdict, it should be
demoted or removed by the nightly consolidation action. That requires consolidation to read
`rca_verdicts`, which it currently can't — a later refinement, not v1.

## 5. Phase 4 — Measurement and human signal

### 5.1 Human feedback UI

Two affordances on the incident card:

1. **"What actually fixed this?"** (from §2.5) — the ground-truth box. Primary.
2. **Verdict override.** Show the reflection agent's verdict and let a human correct it.
   A human-corrected verdict is the highest-quality label we can get and should be marked
   distinctly (`captured_by='human'`) so it can be used to evaluate the reflection agent
   itself.

Both go through the Next.js proxy (`forwardRequest` from `@/lib/backend-proxy`), never
directly to Flask. No client-side identity derivation.

### 5.2 Mine `pre_edit` diffs

`artifact_versions.source='pre_edit'` (`postmortem_routes.py:263-269`) is free, already-collected,
human-authored correction data that nothing reads. A human editing the Root Cause section of
a postmortem is an implicit "you got this wrong."

A task that diffs `pre_edit` → current on the Root Cause / Resolution sections and, when the
change is material, writes a `resolution_reports` row with `confidence='extracted'` and
`source='postmortem_edit'`. Cheap, and it works retroactively on existing data.

### 5.3 Accuracy dashboard

Now possible for the first time:
- Verdict distribution over time (`correct` / `partial` / `wrong` / `unverifiable`)
- Accuracy by service, by connector, by severity
- `failure_mode` frequency → tells us *what to fix in the prompt*, e.g. a spike in
  `deploy_blindspot` means the RCA prompt should check deploys earlier
- `unverifiable` rate → a resolve-note-quality metric we can hand back to the customer
- MTTR, which finally works once §2.2 lands

### 5.4 Structured confidence on the conclusion

`prompt/rca_sections/conclusion_gate.md:19-21` already makes the agent classify
CONFIRMED / LIKELY / INCONCLUSIVE — it's just thrown away in prose. Persist it as
`incidents.conclusion_confidence`. Then we can measure calibration: *are our CONFIRMED
conclusions actually more often correct than our LIKELY ones?* If not, the gate is broken.

## 7. Risks

- **Garbage resolve notes.** Most real-world notes are "fixed" or "restarted". The
  `unverifiable` verdict handles this honestly, but early accuracy data will be thin. This
  is why §2.5 (human UI) and §2.4 (Slack) matter — they're the sources with actual substance.
- **Bad lessons poisoning memory.** Mitigated by: shadow mode default, `partial`/`wrong`
  only, `unverifiable` bias, append-with-dedup instead of entry-per-incident, and the
  existing nightly consolidation. `memory.md:23`'s warning stays in place.
- **Reflection agent grading its own homework.** It judges a conclusion produced by the same
  model family. Some self-serving bias is likely. The §5.1 human verdict override is the
  control — and in shadow mode we can measure agreement before trusting it.
- **Context bloat.** Every retrieval win in Phase 3 costs RCA context. Return sections, not
  documents; filter the index by service.
- **Privacy.** `resolution_text` is customer content and `author_external` is a real handle.
  Never log either. Never use either in a test fixture — synthesize fixtures per the
  no-real-production-data rule.
- **Cost.** Reflection is one extra LLM call per resolved incident, plus one small extraction
  call per harvested Slack thread. Both are cheap relative to an RCA run, but they must go
  through the existing billing hook / `tracked_invoke` path.
