# Decisions

This file records the choices a reader could disagree with. A value that comes from `aurora-lab` lives in `scenario_12.yaml` and `PROVENANCE.md`; the rows here are the decisions that are ours, frozen before code depends on them. Changing one is a new decision with a new number, never a silent edit.

| ID | Decision | Frozen value | Why |
|---|---|---|---|
| D1 | Submission repo, branch and pull request | Fork of `Arvo-AI/aurora` under `kpnaranj/aurora`, branch `kpnaranj/remediation-verifier`, draft pull request against `main` | The one-pager asks for a fork, a branch and a draft pull request. Every change stays inside `remediation-verifier/`, which is R10. |
| D2 | Observation window | 60 seconds | The runbook watches two batch cycles of five seconds (`scenarios/12-two-faults-oom-and-selector/README.md#L202`). 60 seconds leaves room for a rollout and one restart inside the same window. |
| D3 | Processing evidence | At least 2 lines matching `processed batch of <current BATCH_SIZE> items`, batch size read from `deploy/worker` | The pattern is the worker's own line (`app/shop.yaml#L73`), the count is the runbook's two cycles, and reading the batch size from the Deployment keeps a fix that leaves 2500 valid. |
| D4 | HTTP probe | 3 GET requests to `http://frontend.shop.svc.cluster.local/api/items`, two seconds apart, five second timeout, status 200, body `items` equal to the list in `app/shop.yaml#L48` | One request can answer from a single lucky pod. Three requests still fit inside the window and follow the client path the load generator uses. |
| D5 | Full fix | Remove `/spec/selector/tier` with a JSON patch, then `kubectl -n shop set env deploy/worker BATCH_SIZE=500`, frontend first | These are the runbook's own commands (`scenarios/12-two-faults-oom-and-selector/README.md#L164`, `#L170`, `#L180`). A strategic merge patch keeps `tier`, and so does re-applying the manifest. |
| D6 | Partial fixes and no-op | The inverse of each `break.sh` line, and the deliberate absence of a change | Derived from the mechanism that injected each fault (`scenarios/12-two-faults-oom-and-selector/break.sh#L1`, `#L2`), not invented. The no-op is the control that a familiar cluster cannot turn green. |
| D7 | Alternative fix (P1) | Raise `resources.limits.memory` above 244 MiB and remove `/spec/selector/tier`, keeping `BATCH_SIZE=2500` | `scenarios/12-two-faults-oom-and-selector/scenario.yaml#L18` allows raising the limit with the reason stated. 244 MiB is 2500 items of 100 KiB (`app/shop.yaml#L72`). Optional, built in case 8 if the clock allows. |
| D8 | Default mode | `snapshot` | It needs no cluster, no network and no credentials. `make doctor` reported the docker daemon as WARN on 2026-11-15, so SNAPSHOT is the mode this machine can always run. |
| D9 | LIVE mode | Implemented, and declared not tested until a Kind run succeeds | The JUEZ allows declaring LIVE untested. A declared gap costs evidence points; a fake LIVE run is a disqualifier (R1). |
| D10 | CI topology | Workflow template at `ci/github-actions-verify.yml`, run from a separate `ci` branch | A root `.github/workflows/` file would break R10. The template is copied to a branch that publishes only CI. |
| D11 | Restart strictness | 0 restarts at window start and 0 at window end, on the same pod UID | A plain not-increasing check passes at baseline while a CrashLoopBackOff backoff is longer than the window. Requiring a clean pod makes the check fail at baseline and pass for every valid remediation. |
| D12 | Dev-only tooling | `ruff 0.17.5`, `mypy 2.4.1`, `pytest 9.2.0`, runtime `PyYAML 6.0.3` | The runtime dependency is PyYAML. `ruff` and `mypy` are never imported by `verifier/` and do not ship, and `pytest` is the test runner the assessment names. These versions were resolved by `make install` on 2026-11-15 with Python 3.12.3, so they are recorded, not guessed. `pyproject.toml` keeps its declared bounds. |
| D13 | Coverage and hooks | No `pytest-cov`, no `pre-commit` | A coverage percentage says nothing about six checks, and a hook can be skipped. `make ci` and the workflow are the gates. |
| D14 | Commits and branch name | Conventional Commits as `type(verifier): summary (case N)`, branch `kpnaranj/remediation-verifier` | It matches the repository history, for example `fix(prediscovery): schedule it only when a provider is newly connected (#821)`. The branch name deviates from `CONTRIBUTING.md#L148-L167`, which asks for a lowercase prefix, so the deviation is written here instead of hidden. |
| D15 | Test layout | `tests/test_<subject>.py`, classes `Test<Subject>`, sentence-style test names | It mirrors `server/tests/services/test_change_gating_adapter.py` at the fork base, so a reader of Aurora's tests finds the same shape here. |
| D16 | Style contract | `from __future__ import annotations`, a module `LOGGER`, frozen dataclasses, constants with a unit suffix such as `COMMAND_TIMEOUT_S` | Taken from `server/chat/backend/agent/access/mode_access_controller.py` at the fork base, and already used by `verifier/doctor.py`. |
| D17 | README content | Opening Aurora citation with its URL, the five-variant table, the two-year SDLC paragraph, and the JUEZ section 8 sentence verbatim | The JUEZ asks for all four explicitly, in criteria 1.1 and 1.5 and in its evidence checklist. |
| D18 | No web UI | Markdown and JSON reports only | R10 and D12 keep the surface small. The evidence an incident thread can carry is a JSON file plus a Markdown report. |
| D19 | Contract shape | Deltas from the planning draft: `observation.window_seconds` at the oracle level, a `source` on every check and fix, request parameters instead of one route string, and no `provenance` block inside the YAML | One window applies to the whole run. The per-check `source` is what the report prints. The provenance table lives in `PROVENANCE.md` only, because a second machine-readable copy drifts. |
| D20 | Provenance rule | Every cited path and line anchor appears in `PROVENANCE.md`, and one pinned commit applies to every row | This is R4 and R7. A row without a source is not used, and a fixture that cannot be traced is deleted instead of kept. |
| D21 | Window opens late | The runner waits for `kubectl rollout status deploy/worker` and a non-empty frontend EndpointSlice before the window starts | A stale OOMKilled pod, or an empty slice during a rollout, would report a valid fix as a failure. |
| D22 | Baseline gates every verdict | No variant can be positive unless the baseline run confirmed both faults | A fix cannot be verified against an incident that did not reproduce in the same run. |
| D23 | Two endpoint checks, not one | `service_has_endpoints` reads the EndpointSlice addresses and `endpoints_ready` reads `conditions.ready` on those addresses | A pod's address joins the slice before the pod passes readiness, so a selector change that points at a pod still starting passes the first check and fails the second. Read together the two checks also name the failure: no address means the selector matches nothing, an unready address means the pod is not serving yet. |
| D24 | Code size limits | Module 300 lines soft and 400 hard, function 40 and 50, complexity 10, nesting 3, line length 100 | Six checks in one module stay readable while each one fits on a screen. `ruff` enforces the complexity at 10 (`C90`) and the line length at 100 (`E501`), so those two fail the build. Line counts and nesting are reviewed by hand because `ruff` does not measure them, and the soft limit is where a module is split before it reaches the hard one. |
| D25 | Configuration surface | `verifier/config.py` holds the paths, the encoding, the schema name and the lab pin; `REMEDIATION_VERIFIER_CONTRACT` overrides the contract path, and the schema is resolved as a sibling of whichever contract is loaded | A second scenario then costs a pair of files, not a code change. The pin has one definition and `doctor` imports it, so the machine check and the contract cannot disagree without a test failing. |
| D26 | Model and loader split | Frozen dataclasses in `verifier/model.py`; loading, validation and the two views in `verifier/contract.py` | D24 caps a module at 300 lines soft, and the ten types plus the loader reached 419. The split also lets later modules import the types without importing the YAML reader. |
| D27 | Views are a shape, not a filter | `AgentView` has one field, `alert`, and `agent_view()` builds its dictionary from it | R6 asks that the oracle never reach the agent. Copying the contract and deleting keys leaves the next added key exposed; a one-field type has nothing to delete. A test serializes the view and fails on oracle vocabulary, and a second test proves that detector catches a planted key. |
| D28 | Type stubs for PyYAML | A mypy override (`ignore_missing_imports` for `yaml`) instead of the `types-PyYAML` package | D12 allows `ruff` and `mypy` as dev tooling and nothing else. One module imports PyYAML and narrows the result to a mapping before anything else reads it, so the loss is confined to that call. |
| D29 | Structure raises, metadata values are reported | A section or field of the wrong JSON type raises `ObservationError`; a structurally valid value that cannot be used (a naive timestamp, a provenance label other than `LIVE`, an empty commit) is listed in `missing_metadata`, and `require_complete()` is the strict door that raises | R11 says a snapshot missing metadata produces INCONCLUSIVE, and aborting the run would leave no verdict at all. A boolean written as the string `"true"` is a corrupt document, so it fails loudly instead of becoming a silent `false`. |
| D30 | Four modules for the observation layer | `model.py` holds every frozen type; `observations.py` parses snapshots; `live.py` collects and normalizes kubectl output; `kubectl.py` wraps the binary and the HTTP probe | D24 caps a module at 300 lines and the schema plus both collectors reached 778. The split also makes "SNAPSHOT never calls Kubernetes" a property of the imports: nothing on the snapshot path imports `live.py` or `kubectl.py`. |
| D31 | Load generator logs | `kubectl -n shop logs deployment/loadgen --since=<window>s`, captured as supporting evidence and allowed to be empty | `app/shop.yaml#L236-L243` declares the deployment, and its tail shows what a user saw during the window. It is not required metadata, so a missing tail logs a warning instead of aborting a capture. |
| D32 | Snapshot schema artifact | `contracts/snapshot_schema.json`, checked by the same local validator as the contract, with no required sections | The plan asks for a snapshot schema. Requiring sections would turn a missing one into an exception, which contradicts R11: absence must produce INCONCLUSIVE. So the schema checks the type of every section that is present, and the parser still reports what is missing. |
| D33 | Timing is measured, never snapshotted | `from_live` times the pods, services, endpoints, http and logs phases, merges caller phases, and `snapshot_document` omits timing | A duration differs on every run, so writing it would break the byte-identical snapshot the tests need. The live report can still show how long each phase took. |
| D34 | The batch size travels with the observation | A `worker` section carrying `batch_size`, read from `deploy/worker` in LIVE and required by `processing_evidence`; absent or non-positive is reported as `batch_size` in `missing_metadata` | The check compares the number in the log line with the current value, so a line left from an earlier run cannot satisfy it. A SNAPSHOT run has no cluster to ask, so the value has to be part of the capture or the check would guess. |
| D35 | A check reads only the capture | The six checks take the contract and one or two `Observations`, never `kubectl`, the clock or the network; each returns `CheckResult(id, fault, status, reason, source, evidence)` | LIVE and SNAPSHOT must reach the same verdict from the same bytes (R1, R11). A check that queried the cluster would make SNAPSHOT depend on one, and the evidence would stop being reproducible. `source` comes from the contract declaration, so a result cannot cite a path the contract does not carry. |
| D36 | Results live in `verifier/results.py` | `build_result`, the declaration lookup and the evidence builders sit in `results.py`; `checks.py` holds the six checks, `run_checks` and `weak_check_ids` | The first draft of `checks.py` reached 431 lines, over the 400 hard limit in D24. The split keeps each check readable and leaves result construction in one place, so `id`, `fault` and `source` are never retyped by hand. |
| D37 | A baseline pass is reported as weak | `weak_check_ids(results)` returns every PASS, and a reproduction verdict carries that list; a remediation verdict carries an empty list | The rubric asks for a weak-check rate with a denominator, and a weak check is one that passes on the baseline. A remediation's passes are the point of the run, not a defect, so reporting them as weak would mislabel the evidence. The results still carry every pass, so nothing is hidden. |
| D38 | Reproduction status has three values | `CONFIRMED`, `NOT_CONFIRMED` and `UNMEASURED`; `UNMEASURED` means the run could not measure the fault and no positive verdict follows | The rubric names two values, but it also asks how a baseline `NOT_CONFIRMED` caused by the environment is distinguished from one where the fault is absent. Forcing an unmeasured run into `NOT_CONFIRMED` would answer "the fault is absent" when the truth is "nobody looked". An environment failure is `EXECUTION_ERROR`, an absent fault is `NOT_CONFIRMED`, and missing evidence is `UNMEASURED`. |
| D39 | Decision precedence | No positive without a `CONFIRMED` pre-fix state; then any `FAIL` is `REJECTED`; then any unresolved check is `INCONCLUSIVE`; only then `VERIFIED_WITHIN_CONTRACT`, and only with every declared check passing | A failure is decisive and needs no more evidence. Missing evidence is not a failure and must not become one. The positive state is the narrowest one, so it can only be reached by six passes on a run whose baseline confirmed the incident. A run with fewer results than the contract declares is `INCONCLUSIVE`. |
| D40 | The verdict lives in `verifier/decision.py` | `Verdict` and `UnresolvedElement` are frozen types defined there, not in `model.py`; every unresolved element carries the check id, the contract `source` and what was missing | `model.py` holds what a loader builds, and a verdict is built by a rule, not parsed. `UnresolvedElement` carries the source line because R7 asks every claim to cite a path and a line, and the report can then name which rule could not be resolved and where it is written. |
| D41 | The report is a projection of the verdict | `report.py` builds the document from a `Verdict` plus the capture mode and date; it never re-runs a check, never reads the cluster, and refuses a positive verdict whose results carry no evidence | A second calculation in the report would drift from the decision. Keeping one source of truth also lets the JSON and the Markdown read the same verdict. `generated_at` is the only volatile field and the caller passes it, so the same evidence writes the same bytes. |
| D42 | Every metric carries a denominator | `fault_detection` and `weak_checks` are `{"numerator": n, "checks": 6}`, `remediation` counts carry `runs`, and `runs_per_variant` records the real N; a metric with no baseline is `null`, never `0` | R9 asks for the denominator, and a zero would read as "measured and found none" when the truth is "there was no baseline to measure". `runs_per_variant` is how a repetition count stays visible instead of being averaged away. |
| D43 | A terminating pod is not a current pod | The capture marks `Pod.terminating` from `metadata.deletionTimestamp`; the two window checks count only the pods that are not terminating; the evidence keeps every pod and names the ones it left out | `kubectl get pods` keeps listing a pod while it terminates, and `kubectl rollout status` returns once the new pod is available, so an OOMKilled pod from the old ReplicaSet can still answer the query behind a healthy one. Counting it would fail a fix that worked. Kubernetes describes the matching endpoint rule as `ready` = serving and not terminating, and a terminating endpoint always reports `ready: false` (https://kubernetes.io/docs/concepts/services-networking/endpoint-slices/), so the pod-level rule and the endpoint-level rule are the same idea. |
| D44 | The runner is split from the lab | `verifier/runner.py` holds the order, the `Session` protocol, the plan and the attempt; `verifier/lab.py` holds the lab path, the kubeconfig, the child environment and `LiveSession` | D24 caps a module at 300 lines, and the split keeps "what a run does" separate from "how a cluster is reached". It also lets the sequence run against a simulated session, which is the only way to test it on a machine without Docker (D9). |
| D45 | The kubeconfig is pinned, never inherited | Every kubectl call carries `--kubeconfig <lab>/.kubeconfig --context kind-<cluster>`, and every child process gets a minimal environment whose `KUBECONFIG` is the lab file | `lab.sh` already exports those two values (lab.sh#L14-L18). Passing them explicitly and dropping the rest of the shell environment means a `KUBECONFIG` exported for another cluster cannot redirect a run, which is the failure mode a reviewer would fear most. |
| D46 | A LIVE window has two captures | The runner captures the state at the start of the window, sleeps the contract's `window_seconds`, and captures again; the checks read both. A SNAPSHOT document is one point in time and is used for both ends | The two window checks compare a start and an end. A snapshot cannot observe a change, so it stands in for both, and the restart rule still fails a capture whose start is not clean (D11). The limitation is printed in the report's `## Limitations`. |
| D47 | An empty slice after the wait is evidence, not a failure to execute | `wait_endpoints` returns False when the budget expires; the runner opens the window anyway and the two endpoint checks decide. A kubectl error still raises and becomes EXECUTION_ERROR | A partial fix that leaves the selector broken must read as REJECTED with `service_has_endpoints` failing, which is the incident's second fault. Calling that EXECUTION_ERROR would say the verifier broke, hide the finding, and make the table less useful. A command that fails is different: then the verifier did not look. |
| D48 | A remediation is gated twice | The cycle's baseline must be CONFIRMED and the variant's own pre-fix capture must fail all six checks; the pre-fix gate is a reproduction verdict built from that capture, and a non-CONFIRMED gate makes `decide_remediation` return INCONCLUSIVE | D22 and the rubric ask for both: no positive without a reproduced incident, and no positive for a variant whose pre-fix state was not confirmed. Using the same decision function for the gate means the rule is not reimplemented in the runner. |
| D49 | A failed variant stays local | `LiveError`, `ObservationError`, `OSError` and `RunnerError` become EXECUTION_ERROR for that variant, and the run continues; a `ContractError` still raises because it is a defect in the contract or in the caller | One variant that cannot finish should not erase the evidence of the others. A misdeclared fix or an unknown variant is not a cluster problem, so it must not be reported as one. |
| D50 | A fix step is argv, never a shell | Each contract step is split with `shlex.split`, the program has to be `kubectl`, and the remaining arguments go to the wrapper that already carries the lab kubeconfig | The steps are literals from the frozen contract, but parsing them without a shell means a step can only run kubectl with the arguments the contract names. A shell would turn a contract typo into an arbitrary command, and R10 keeps the verifier read-only about the lab. |
| D51 | Three test layers for one sequence | `test_runner.py` fixes the order with a simulated session; `test_runner_cluster.py` runs the real collector, checks and decision over a simulated cluster with ten failure modes; `test_lab.py` runs a real subprocess against a fake kubectl to fix argv, environment, exit code and timeout | Each layer covers what the others cannot. The protocol fake proves the sequence, the simulated cluster proves the verdicts, and the subprocess proves the LIVE plumbing. None of them needs Docker, and none of them claims to be a cluster run. |
| D52 | The worker log comes from the pod the capture counted | `from_live` reads `kubectl -n shop logs pod/<current pod> --since=<window>s`, using the pod the same capture listed and did not mark terminating; with no current pod the log is empty and a warning is logged | `kubectl logs deployment/x` picks one pod and prints which one it picked (https://kubernetes.io/docs/tutorials/configuration/updating-configuration-via-a-configmap/), so during a rollout it can return the pod that is terminating. `processing_evidence` compares the log with the current `BATCH_SIZE`, so a line from another container instance would be the wrong evidence. An empty log lets the check fail with its own evidence instead of aborting the capture. |
| D53 | The HTTP check runs inside the cluster | `probe_in_cluster` runs `kubectl exec deployment/loadgen -- sh -c 'wget -q -S -O - -T <timeout> <route>; echo RV_EXIT:$?'` and reads the last `HTTP/x NNN` line and the JSON body; the host `urllib` probe is gone | The first LIVE baseline failed the HTTP check with `Name or service not known`: the verifier runs on the host, which cannot resolve a cluster-internal Service name, and the same failure would reject a correct fix. The load generator is the client the runbook reads (`app/shop.yaml#L256-L257`), it already has wget, and it sits on the user path. The shell always exits 0, so a 503 is evidence about the Service and not a command failure. |
| D54 | The lab settle is zero | `LiveSession` passes `SETTLE=0` to `lab.sh break`; the value is a constructor parameter and defaults to zero | `lab.sh` sleeps 45s after `check.sh` proves both faults so backoff counts accumulate. The baseline gate needs a pod that has already OOMKilled and an empty slice, which `check.sh` guarantees, and the verifier opens its own 60s window after the fix. Measured on 2026-11-16 against the Kind cluster: break 100.7s before, 56.4s after, with the same six FAIL results at baseline. |
| D55 | The capture overlaps its reads with the probe, and the endpoint wait is pacing | `from_live` runs the three HTTP probes in a thread while it reads the deployment, pods, service and endpoint slice, then joins both log reads in a second pool; `Plan` waits 5s for an endpoint with a 1s poll | The probes are spaced by the contract's two-second interval, so they cost at least four seconds; the kubectl reads fit inside that wait. The endpoint wait decides nothing: if the slice is still empty the window runs and the two endpoint checks read the end capture, so a shorter wait loses no evidence and saves up to 55s on a variant that leaves the selector broken. Five seconds is still several times what the EndpointSlice controller needs on this cluster. |
| D56 | Exit codes carry no verdict | `0` when the report was written, whatever the verdicts; `2` when nothing ran (usage, contract, missing fixture, lab not at the pin); `3` when the verifier crashed | R2: a non-zero exit on REJECTED would let a pipeline block a merge on the verifier's opinion. `2` separates "the operator can fix this" from `3` "this is a bug", so CI can tell a broken fixture from a rejected fix. |
| D57 | The baseline fixture is the pre-fix state of a SNAPSHOT remediation | `snapshots.verify` decides the baseline first, then passes that verdict as the gate of every remediation; each remediation document stands for both ends of its window | LIVE breaks the cluster once per variant and captures its own pre-fix state (D48). SNAPSHOT has no cluster: after reset and break the state is the baseline's, and the baseline fixture is the capture that proves it. A second document per remediation would add a file without adding evidence, and a remediation without a confirmed baseline still cannot be positive. |
| D58 | A capture proves the lab commit | `--mode capture` reads `git -C <lab> rev-parse HEAD` and refuses to run when it differs from `contract.source.commit` or cannot be read; `from_live` records that commit in `meta.lab_commit` | A fixture claims a lab commit. Without the guard the claim comes from the contract while the cluster may have run another revision, which breaks R4 and R7. Refusing costs nothing; a fixture with the wrong provenance costs the whole evidence set. |
