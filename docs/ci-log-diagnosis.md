# Option A: a first diagnosis from a CI log

## Argument

Target: an engineer evaluating Aurora who has a failed build but cannot yet grant
access to production or install a GitHub app. The assessment describes weeks of
security review, integration work and waiting for an incident before first value.
This path starts with something the engineer already has: a short CI log.

From onboarding (or the empty incidents screen), paste an excerpt, review the
provider disclosure, consent, and receive a likely cause with cited lines, a
suggested next step and a way to verify it. Ambiguous logs ask for more evidence.
The included TypeScript sample makes the interaction discoverable without an
upload. It still calls the configured model; there is no canned production answer.

The hypothesis is a useful result within two minutes of opening the page on an
already running, model-configured instance. This is a target, not a measured
outcome. Account creation, self-host setup and administrator model configuration
remain prerequisites; this change does not solve those onboarding costs.

## Implementation and boundaries

- `/onboarding/diagnose` → Next `/api/ci-diagnosis` proxy → Flask blueprint → one
  model invocation using Aurora's existing provider factory and summarization model.
- Identity comes from the server session. The backend requires `chat:write`, an
  organization, and the existing entitlement and pre-LLM hooks.
- No repository access, connectors, agent loop, tool binding or command execution.
  Log instructions are explicitly untrusted in the prompt. This limits capabilities;
  it does not prove that every generated suggestion is safe or correct.
- Maximum 20,000 characters / 1,000 lines, a 150,000-byte JSON envelope, 2,000 output
  tokens, 16,000 response characters, and five citations of at most eight lines.
  Provider requests use a 45-second timeout and no SDK retries where supported;
  the proxy and browser time out at 55 and 60 seconds. These are request timeouts,
  not a guarantee that upstream work stops when the browser disconnects.
- Strict schema and range validation reject malformed or unsupported output.
  Quotes are reconstructed from the submitted log, never generated by the model.
  Citation existence is validated; semantic support still needs human evaluation.
- Consent is required and resets on edits. Users must remove secrets themselves;
  there is no automatic redaction. The configured provider receives the excerpt
  and its retention policy applies. No log/diagnosis is saved to chat or a new DB
  record. LangSmith tracing is disabled for the invocation. Existing usage tracking
  stores token/cost metadata; operational logs contain counts, status and timing.
- Responses use `Cache-Control: no-store`; all displayed content is plain React
  text. Reloading or leaving loses the result. Errors preserve input for retry.
- The endpoint declares 5 requests/minute and 30/hour through the shared limiter.
  Enforcement follows the deployment's global enablement and exemptions (including
  trusted/local traffic); the default disabled limiter is not a cost-control guarantee.

## Try it

On an existing Aurora installation built from this branch, sign in and open
`/onboarding`, choose **Try Aurora on a failed build**, then **Use a sample log**.
Review the disclosure, check consent, and analyze. For your own failure, paste the
failed command and surrounding error output. A lone exit code should request more
context rather than invent a fix.

For a source deployment, follow the repository setup and use `make prod-local`
instead of `make prod-prebuilt` so the new code is included. Use an isolated local
environment with the existing development credentials and exposed services
appropriately restricted. This submission did not start or validate the full
Docker stack.

The model uses existing `SUMMARIZATION_MODEL` configuration (falling back through
`MAIN_MODEL` to Aurora's default). For example, an administrator can configure
`SUMMARIZATION_MODEL=openai/gpt-4.1-mini` with an `OPENAI_API_KEY` in their local
environment. No new environment variables or dependencies are required by the
feature. Never commit keys. No live provider request was made during this task.

## Validation

From the repository root, with backend dependencies installed and `PYTHONPATH=server`:

```sh
python -m pytest server/tests/services/test_ci_diagnosis.py server/tests/routes/test_ci_diagnosis_routes.py -q
```

46 passing tests cover input limits, evidence integrity, insufficient evidence,
the single tool-free model boundary, safe failures, real Flask/RBAC handling,
organization gates, server-derived identity and an enabled rate limiter. Provider,
identity storage, billing and database I/O are stubbed; this is not full-stack coverage.

From `client`, after `npm ci --ignore-scripts` and installing a Playwright browser:

```sh
npx playwright test --config tests/ci-diagnosis.config.ts
```

Alternatively set `PLAYWRIGHT_CHANNEL=chrome` to use an installed Chrome. Ports
3000 and 5089 must be free. The dedicated config starts a local Next server with
test-only auth configuration; the suite supplies a fake backend and synthetic
account. Seven passing browser tests cover onboarding, consent, evidence display,
escaping, retry, size rejection, mobile width, unauthenticated rejection and the
real Next proxy's identity headers. Browser responses are fixtures: displayed
timings in test screenshots are not latency measurements. No LLM key is needed.

Full TypeScript checking reports the same 32 diagnostics on the base revision
`12c67cffd45c6b0b8c5da1d2e160a945e2936f49` and this branch after generating Next route
types (normalized paths and shifted line numbers). None is introduced by this
feature. The repository's lint command also encounters an existing
`minimatch` default-export incompatibility. `npm run build` passes; the existing
Next configuration skips type checking and linting during that build, which is
why those checks are reported separately.

## What I would do next

Run a live evaluation with five engineers and sanitized examples spanning a
compiler failure, test failure, dependency failure, infrastructure failure and
insufficient evidence. Record time from page open to the first diagnosis the
engineer rates actionable, citation correctness, wrong/confident suggestions,
provider failures and per-request cost. Compare with the current onboarding path;
target a median under two minutes, without treating a rendered response as success.

The UI currently shows elapsed time since page open and analysis duration; the
backend emits content-free started/completed/failed events and usage metadata.
These provide diagnostics, not a persisted user-level activation funnel. Add a
small content-free usefulness/funnel instrument after validating the interaction.
Then decide whether saved results or an investigation handoff merits expanding
scope. Before rollout, also test provider compatibility, configured cost limits,
prompt injection, sensitive-log handling and the full deployment.
